在搜索改写任务中，评估模型生成的改写查询（候选）的质量至关重要。通常从两个维度进行评价：**与人工参考改写的相似度**（即文本生成质量）和**语言流畅度**。BLEU 和 METEOR 主要用于前者，而 Perplexity（PPL）用于后者。下面详细解释它们的定义、计算方式及适用场景。

---

## 1. BLEU（Bilingual Evaluation Understudy）

BLEU 最初用于机器翻译，后来广泛用于各种文本生成任务。它通过比较候选文本与一个或多个参考文本之间的 **n-gram 重叠** 来评估相似度。

+ Bilingual (双语): 最初用于评估机器翻译，涉及源语言和目标语言两种语言
+ Evaluation (评估/评测): 用于评价翻译质量
+ Understudy (替补/候补): 意指作为人工评估的替代方案

### 核心思想

- 统计候选句中 n-gram（连续 n 个词）在参考句中出现的次数。
- 计算 **精确率**（Precision），即候选句中 n-gram 有多少是合理的。
- 引入 **简短惩罚**（Brevity Penalty），防止生成过短的句子获得高分。

### 计算步骤

1. **分词**：将候选句和参考句分词（通常按空格或子词划分）。
2. **计算 n-gram 匹配数**：对于 n=1,2,3,4，统计候选句中每个 n-gram 在参考句中出现的最大次数（截断计数，避免重复奖励）。
   - 例如候选句有 3 个相同的 bigram，但参考句只有 2 个，则匹配数计为 2。
3. **计算 n-gram 精确率**：
   \[
   p_n = \frac{\sum_{\text{n-gram} \in \text{Candidate}} \text{Count}_{\text{clip}}(\text{n-gram})}{\sum_{\text{n-gram} \in \text{Candidate}} \text{Count}(\text{n-gram})}
   \]
   即所有匹配上的 n-gram 数量除以候选句中所有 n-gram 数量。
4. **几何平均**：将各 n-gram 的精确率取对数加权平均，通常使用均匀权重 \(w_n = 1/4\)：
   \[
   \text{BLEU} = \text{BP} \cdot \exp\left( \sum_{n=1}^4 w_n \log p_n \right)
   \]
5. **简短惩罚**：
   \[
   \text{BP} = 
   \begin{cases} 
   1 & \text{if } c > r \\
   e^{(1 - r/c)} & \text{if } c \le r
   \end{cases}
   \]
   其中 \(c\) 是候选句长度，\(r\) 是参考句的有效长度（通常取最接近 \(c\) 的参考句长度）。若候选句短于参考句，BP < 1，惩罚过短译文。

### 在搜索改写中的应用

在查询改写任务中，BLEU 用于衡量：

改写后的查询 与 人工标注的高质量改写 之间的相似度
n-gram 匹配度越高，说明改写越接近人工标准

### 优点与局限

- **优点**：计算简单、与人类评价有一定相关性，是事实上的标准指标。
- **局限**：
  - 仅基于 n-gram 表面匹配，不考虑语义相似性。
  - 对同义词、词形变化不敏感（例如“run”和“ran”被视为不同）。
  - 简短惩罚过于简单，有时会误判。

在搜索改写中，BLEU 可以衡量改写查询与人工标注的高质量改写之间的词汇重叠度，但可能忽略那些用词不同但语义等价的改写。

# ROUGE 指标详解及其与 BLEU 的区别

## 📊 ROUGE (Recall-Oriented Understudy for Gisting Evaluation)

### 定义

**ROUGE** 是一种用于评估**文本摘要**质量的自动评估指标，由 Chin-Yew Lin 在 2004 年提出。它通过比较**候选摘要**与**参考摘要**之间的重叠度来评估生成质量。

### 核心思想

- **基于召回率 (Recall)**: 关注参考摘要中有多少内容被包含在生成摘要中
- **N-gram 匹配**: 计算 n-gram 的重叠程度
- **F1-Score**: 综合精确率和召回率

---

## 🔢 ROUGE 的主要变体

### 1. **ROUGE-N**

基于 n-gram 的匹配度

```python
ROUGE-N = Σ(Count_match(gram_n)) / Σ(Count(gram_n_in_reference))
```

**示例**:

```
参考摘要：我今天去公园玩
生成摘要：今天我去公园

ROUGE-1 (unigram):
- 参考 unigrams: {我，今，天，去，公，园，玩} (7 个)
- 生成 unigrams: {今，天，我，去，公，园} (6 个)
- 匹配 unigrams: {我，今，天，去，公，园} (6 个)
- Recall = 6/7 = 0.857
- Precision = 6/6 = 1.0
- F1 = 2 * (0.857 * 1.0) / (0.857 + 1.0) = 0.923
```

### 2. **ROUGE-L**

基于最长公共子序列 (LCS, Longest Common Subsequence)

```python
LCS(X, Y) = X 和 Y 的最长公共子序列长度
ROUGE-L = LCS_length / Reference_length
```

**特点**:

- ✅ 考虑句子级别的语序信息
- ✅ 不需要连续的匹配
- ✅ 对同义词替换更鲁棒

**示例**:

```
参考：我喜欢吃苹果和香蕉
生成：我喜欢苹果香蕉

LCS: {我，喜，欢，苹，果，香，蕉} (长度 7)
ROUGE-L = 7/9 = 0.778
```

### 3. **ROUGE-W**

加权 LCS，给连续匹配更高的权重

### 4. **ROUGE-S**

基于跳字统计 (Skip-bigram)

---

## 🆚 ROUGE vs BLEU 对比

| 维度        | **ROUGE**        | **BLEU**              |
| --------- | ---------------- | --------------------- |
| **提出时间**  | 2004 年           | 2002 年                |
| **主要用途**  | **文本摘要**评估       | **机器翻译**评估            |
| **优化目标**  | **召回率 (Recall)** | **精确率 (Precision)**   |
| **计算基准**  | 参考文本的 n-gram     | 生成文本的 n-gram          |
| **分母**    | 参考摘要长度           | 生成摘要长度                |
| **长度惩罚**  | 无显式惩罚            | 有 BP(Brevity Penalty) |
| **语序考虑**  | ROUGE-L 考虑语序     | BLEU 不考虑长距离语序         |
| **多参考支持** | 支持多个参考摘要         | 支持多个参考译文              |

---

## 📐 数学公式对比

### ROUGE 公式

```python
# ROUGE-N Recall
Recall_ROUGE = Count_match(gram_n) / Count(gram_n_in_reference)

# ROUGE-N Precision  
Precision_ROUGE = Count_match(gram_n) / Count(gram_n_in_candidate)

# ROUGE-N F1
F1_ROUGE = 2 * Precision * Recall / (Precision + Recall)
```

### BLEU 公式

```python
# n-gram 精确率
P_n = Count_match(gram_n) / Count(gram_n_in_candidate)

# 组合精确率 (几何平均)
BLEU = BP * exp(Σ w_n * log(P_n))

# 简短惩罚 (BP)
BP = 1 if c > r else exp(1 - r/c)
# c = 生成长度，r = 参考长度
```

---

## 💡 实际计算示例

### 示例数据

```python
参考摘要：猫坐在垫子上
生成摘要 A：猫在垫子上
生成摘要 B：垫子上有一只猫
```

### ROUGE-1 计算

```python
# 生成摘要 A
参考 unigrams: {猫，坐，在，垫，子，上} (6 个)
生成 unigrams: {猫，在，垫，子，上} (5 个)
匹配：{猫，在，垫，子，上} (5 个)

Recall_A = 5/6 = 0.833
Precision_A = 5/5 = 1.0
F1_A = 0.909

# 生成摘要 B
参考 unigrams: {猫，坐，在，垫，子，上} (6 个)
生成 unigrams: {垫，子，上，有，一，只，猫} (7 个)
匹配：{猫，垫，子，上} (4 个)

Recall_B = 4/6 = 0.667
Precision_B = 4/7 = 0.571
F1_B = 0.615
```

### BLEU-1 计算

```python
# 生成摘要 A
P_1 = 5/5 = 1.0
BP = exp(1 - 6/5) = 0.819 (因为生成比参考短)
BLEU-1 = 0.819 * 1.0 = 0.819

# 生成摘要 B
P_1 = 4/7 = 0.571
BP = 1.0 (因为生成比参考长)
BLEU-1 = 1.0 * 0.571 = 0.571
```

## 🎯 适用场景对比

### ✅ 使用 ROUGE 的场景

1. **文本摘要任务**
   
   - 新闻摘要生成
   - 文档摘要
   - 对话摘要

2. **问答系统**
   
   - 答案生成质量评估

3. **强调覆盖率**
   
   - 需要确保关键信息不丢失
   - 召回率比精确率更重要

### ✅ 使用 BLEU 的场景

1. **机器翻译任务**
   
   - 多语言翻译质量评估

2. **强调准确性**
   
   - 生成内容必须准确
   - 不允许冗余信息

3. **代码生成**
   
   - 语法正确性要求高

---

## ⚠️ 共同局限性

### ROUGE 和 BLEU 都有以下问题:

1. **语义理解缺失**
   
   ```
   参考：他非常高兴
   生成：他特别开心
   → ROUGE/BLEU 得分低，但语义相同
   ```

2. **句法多样性忽略**
   
   ```
   参考：猫追老鼠
   生成：老鼠被猫追
   → 被动语态得分低
   ```

3. **依赖参考质量**
   
   - 参考摘要质量差 → 评估不准确
   - 单一参考 → 忽略多样性

4. **长度敏感性**
   
   - ROUGE: 偏好长摘要 (高召回)
   - BLEU: 偏好接近参考长度的输出

## 📊 Python 实现示例

```python
from rouge import Rouge
from nltk.translate.bleu_score import sentence_bleu

# ROUGE 计算
rouge = Rouge()
reference = "猫坐在垫子上"
candidate = "猫在垫子上"

scores = rouge.get_scores(candidate, reference)
print(f"ROUGE-1 F1: {scores[0]['rouge-1']['f']}")  # 0.909
print(f"ROUGE-L F1: {scores[0]['rouge-l']['f']}")  # 0.857

# BLEU 计算
reference_tokens = list(reference)
candidate_tokens = list(candidate)

bleu_score = sentence_bleu([reference_tokens], candidate_tokens)
print(f"BLEU-1: {bleu_score}")  # 0.819
```

## 2. METEOR（Metric for Evaluation of Translation with Explicit ORdering）

METEOR(显式排序翻译评估指标) 旨在克服 BLEU 的一些缺点，通过引入 **词干化、同义词匹配** 和 **召回率** 来更全面地评价生成文本。

### 核心思想

- 建立候选句与参考句之间的 **unigram 对齐**，允许基于词干（stemming）和同义词库（如 WordNet）的匹配。
- 计算 **精确率** \(P\) 和 **召回率** \(R\)，然后取调和平均。
- 加入 **惩罚因子** 惩罚词序混乱。

### 计算步骤

1. **预处理**：对候选句和参考句进行词干化（如 Porter 词干提取），并利用同义词库扩展匹配。
2. **建立对齐**：寻找候选词与参考词之间的一一对应关系，优先匹配最长可能的序列（使匹配更合理）。
3. **计算精确率与召回率**：
   $P = \frac{m}{\text{候选句长度}}, \quad R = \frac{m}{\text{参考句长度}}$
   其中 \(m\) 是匹配上的 unigram 数量。
4. **调和平均**（通常召回率权重稍高）：
   $F_{\text{mean}} = \frac{10 \cdot P \cdot R}{R + 9P}$
   （权重 9:1 来自经验，强调召回率）
5. **计算碎片惩罚**（Fragmentation Penalty）：
   - 将匹配的词按照它们在候选句中的顺序，与参考句中的顺序进行比较。若匹配词块（chunks）越多，说明词序越乱。
   - 惩罚因子：$\text{Penalty} = 0.5 \times \left( \frac{\text{chunks}}{\text{matches}} \right)^3$
     其中 chunks 是连续匹配的块数，matches 是总匹配数。
6. **最终 METEOR 分数**：$\text{METEOR} = F_{\text{mean}} \times (1 - \text{Penalty})$

### 优点与局限

- **优点**：与人类判断的相关性通常高于 BLEU；考虑同义词和词形，更灵活；引入召回率，鼓励覆盖参考句内容。
- **局限**：需要语言资源（如同义词库），不同语言支持度不一；计算稍复杂；仍基于词匹配，难以捕捉深层语义。

在搜索改写中，METEOR 比 BLEU 更能容忍用词变化，更适合评估那些改写后保留原意但表达不同的查询。

## 3. Perplexity（PPL，困惑度）

Perplexity 是信息论中衡量概率分布预测样本好坏的标准，在 NLP 中用于评估语言模型的生成质量。它反映了模型对测试数据的 **不确定性**，**越低表示模型对文本的预测越准确，生成的句子越流畅**。

### 定义与计算

给定一个语言模型，它对一个词序列 $w_1, w_2, \dots, w_T$ 的联合概率为：
$P(w_1, w_2, \dots, w_T) = \prod_{t=1}^T P(w_t | w_1, \dots, w_{t-1})$

Perplexity 定义为该概率的几何平均的倒数：$\text{PPL} = \left( P(w_1, \dots, w_T) \right)^{-\frac{1}{T}} = \exp\left( -\frac{1}{T} \sum_{t=1}^T \log P(w_t | w_{<t}) \right)
$
等价于指数形式的交叉熵：$\text{PPL} = \exp\left( \frac{1}{T} \sum_{t=1}^T -\log P(w_t | w_{<t}) \right)$

### 直观理解

- 如果模型对每个词的预测概率都很高（接近 1），则 \($\log P$\) 接近 0，PPL 接近 1（最小可能值）。
- 如果模型总是以 0.5 的概率预测下一个词（二选一），则 PPL 约为 2；如果每次要从 1000 个词中均匀猜测，则 PPL 约为 1000。

### 在搜索改写中的应用

- 计算生成查询的 PPL 时，需要使用一个预先训练好的语言模型（如基于 Transformer 的通用 LM）来评估生成句子的概率。
- 若生成的查询语法不通、词序混乱，则语言模型会赋予低概率，导致高 PPL。
- **注意**：PPL 仅反映流畅度，不直接衡量与原始查询的语义相关性。因此通常与 BLEU/METEOR 结合使用。

### 优点与局限

- **优点**：直接反映语言模型的置信度，与人类对流畅度的感知相关；计算方便，只要有一个好的 LM。
- **局限**：依赖 LM 的质量；无法判断语义正确性；对于短文本可能不稳定。

---

## 总结：指标对比

| 指标     | 评估维度 | 计算基础                           | 优点         | 缺点            |
| ------ | ---- | ------------------------------ | ---------- | ------------- |
| BLEU   | 相似度  | n-gram 精确率 + BP                | 简单、标准、广泛使用 | 忽略语义、同义词、召回率  |
| METEOR | 相似度  | unigram 匹配（词干/同义词）+ 召回率 + 词序惩罚 | 更灵活、相关性更高  | 需语言资源、稍复杂     |
| PPL    | 流畅度  | 语言模型概率                         | 直接反映流畅性    | 依赖外部 LM，不反映语义 |

在搜索改写任务中，通常使用 BLEU 或 METEOR 来评估改写后的查询与人工改写参考的接近程度，用 PPL 来确保生成的查询本身语言通顺。结合这两类指标，可以全面衡量模型的生成质量与搜索友好性。
