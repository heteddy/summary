# 执行流程

Agent Skills 的执行流程本质上是一套  **“意图匹配 -> 逻辑加载 -> 任务分解 -> 闭环执行”**   的机制。

为了让你直观理解，我们来看一个具体的例子：**“自动化代码重构技能（Code Refactoring Skill）”**。**“API Key 迁移技能 (Secret-Refactor-Skill)”** 拆解为一个可落地的 Demo，并展示它在后台是如何与大模型（LLM）“对暗号”的。

## 1. Agent Skill 的目录结构 (Demo)

一个典型的 Skill 实际上是一个功能包，Agent 在启动或识别到需求时会加载它：

Plaintext

```
/skills/secret-refactor-skill/
├── definition.json      # 技能元数据：谁能用，什么时候用
├── instructions.md      # 核心逻辑：SOP 标准作业程序（AI 的“脑子”）
└── templates/           # 预设模板：如 .env.example 的格式
```

### 核心：`instructions.md` (部分内容)

> **Role:** 你是一个安全重构专家。 **Workflow:** > 1. 扫描目标文件中的硬编码字符串。 2. **必须** 检查是否已导入 `os` 模块，若无则添加。 3. 将密钥替换为 `os.getenv("VARIABLE_NAME")`。 4. **必须** 同步更新 `.env.example` 文件。

## 1. Agent Skill 的目录结构 (Demo)

一个典型的 Skill 实际上是一个功能包，Agent 在启动或识别到需求时会加载它：

Plaintext

```
/skills/secret-refactor-skill/
├── definition.json      # 技能元数据：谁能用，什么时候用
├── instructions.md      # 核心逻辑：SOP 标准作业程序（AI 的“脑子”）
└── templates/           # 预设模板：如 .env.example 的格式
```

### 核心：`instructions.md` (部分内容)

> **Role:** 你是一个安全重构专家。
> 
> **Workflow:** > 1. 扫描目标文件中的硬编码字符串。
> 
> 2. **必须** 检查是否已导入 `os` 模块，若无则添加。
> 3. 将密钥替换为 `os.getenv("VARIABLE_NAME")`。
> 4. **必须** 同步更新 `.env.example` 文件。

## 2. 大模型与 Skill 的交互流程

### 步骤 A：系统指令注入 (System Prompt Injection)

当 Agent 检测到用户需求与“重构、密钥、安全”相关时，它会将 `instructions.md` 的内容动态拼接到 System Prompt 中。

**交互 JSON (发送给 LLM):**

JSON

```json
{
  "model": "gemini-2.0-flash",
  "messages": [
    {
      "role": "system",
      "content": "You are a helpful assistant with a specialized skill: 'Secret-Refactor'. \nRules: [此处插入 instructions.md 的内容] \nAvailable Tools: read_file, write_file"
    },
    {
      "role": "user",
      "content": "帮我把 app.py 里的 API Key 改成环境变量。"
    }
  ]
}
```

***

### 步骤 B：意图解析与工具调用 (Tool Call)

模型阅读了 Skill 之后，意识到第一步必须先“看”文件。  
**LLM 返回的 JSON (响应):**

```json
{
  "choices": [{
    "message": {
      "role": "assistant",
      "tool_calls": [{
        "id": "call_001",
        "type": "function",
        "function": {
          "name": "read_file",
          "arguments": "{\"path\": \"app.py\"}"
        }
      }]
    }
  }]
}
```

***

### 步骤 C：执行结果反馈 (Tool Result)

Agent 执行本地操作（或通过 MCP Server），将结果喂回给模型。

**交互 JSON (发送给 LLM):**

JSON

```json
{
  "role": "tool",
  "tool_call_id": "call_001",
  "content": "API_KEY = 'sk-123456789'\ndef main():\n    print(API_KEY)"
}
```

***

### 步骤 D：遵循 Skill 规范进行修改 (The "Skill" in Action)

此时，模型不会直接输出代码，而是根据 **Skill 定义的 SOP** 准备执行写操作。注意它如何遵循“必须导入 os”这一规则：

**LLM 返回的 JSON (最终执行指令):**

JSON

```json
{
  "choices": [{
    "message": {
      "role": "assistant",
      "tool_calls": [
        {
          "id": "call_002",
          "type": "function",
          "function": {
            "name": "write_file",
            "arguments": "{\"path\": \"app.py\", \"content\": \"import os\\n\\nAPI_KEY = os.getenv('API_KEY')\\ndef main():\\n    print(API_KEY)\"}"
          }
        },
        {
          "id": "call_003",
          "type": "function",
          "function": {
            "name": "write_file",
            "arguments": "{\"path\": \".env.example\", \"content\": \"API_KEY=your_key_here\"}"
          }
        }
      ]
    }
  }]
}
```

***

## 3. 关键交互结构总结

| **阶段**       | **传输内容 (Data Payload)**    | **目的**                           |
| ------------ | -------------------------- | -------------------------------- |
| **Skill 注入** | `system_message` 包含 SOP 文本 | 给 AI “装脑子”，设定行为边界                |
| **工具请求**     | `tool_calls` 包含函数名和参数      | AI 决定动用“手”（MCP 或本地函数）            |
| **环境响应**     | `tool` 角色返回的执行结果           | AI 获取真实世界的状态（读取的代码）              |
| **多任务并行**    | 数组形式的 `tool_calls`         | Skill 引导 AI 一次性完成多个关联动作（改代码+改配置） |

### 为什么这比普通的 Prompt 厉害？

1. **确定性：** 通过 `instructions.md` 强制要求步骤（如必须生成 `.env.example`），减少了 AI 的随意性。
2. **原子化：** JSON 结构使得整个过程可以被监控和拦截（你可以设置人工审批环节）。
3. **按需：** 只有需要重构时，这部分 JSON 才会出现在上下文里，节省 Token。
